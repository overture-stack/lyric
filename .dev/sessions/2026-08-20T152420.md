Closed a SQL injection reachable through any SQON filter, plus a more severe stored variant found by sweeping the package for the same pattern rather than stopping at the one reported.

- **Why `sql.raw()` was the actual defect, not just this one call site.** `sql.raw()` inlines its argument as literal SQL text with zero escaping; it is only safe when that argument is a compile-time constant. Both vulnerable spots (`convertSqonToQuery.ts`'s `processFilterOperator`, `submittedRepository.ts`'s `getSubmittedDataFiltered`) spliced a caller- or record-controlled value into it. The generalizable fact for this codebase going forward: grep for `sql.raw(` and treat any hit whose argument isn't a `const` string as a live audit target, not a style question. Two of two existing violations turned out to be real; there is no reason to assume the pattern won't recur.
- **Why the second instance mattered more than the first, and why it exists at all.** `convertSqonToQuery.ts`'s injection is request-time: a caller supplies a malicious SQON filter directly. `submittedRepository.ts`'s `getSubmittedDataFiltered` reads `dataValue` back out of a submitter's *own previously-submitted record* to resolve foreign-key relationships (`searchDataRelations.ts`, `viewMode.ts`, `submissionProcessor.ts` all call it this way), so a malicious value submitted once poisons every later query that walks that record's relationships. It was found only because the reported instance was treated as one occurrence of a pattern, not a scope boundary, and the rest of the package was swept before calling the fix done.
- **Why `inArray()` over a hand-rolled `sql` template, beyond it being shorter.** The first working fix used `sql`${jsonbField} IN ${values}``, which is correct (drizzle comma-expands an array into one bound parameter per element, verified directly against real query output) but reinvents a helper the codebase already has: `activeSubmissionRepository.ts` and `submittedRepository.ts` itself use `inArray()` for this exact operation elsewhere. Switching to it wasn't just consistency, it also rejects an empty array with a clear thrown error instead of the hand-rolled version's silent `IN ()`, invalid Postgres syntax that would have surfaced as a confusing runtime error far from its cause. Lesson: reaching for an existing query-builder helper here is worth checking before writing new SQL-construction code, since the helper carries defensive behavior a reimplementation won't include unless deliberately added back.
- **How to test a parameterized-query fix, since the old assertion style doesn't apply.** The prior tests asserted against drizzle's internal `StringChunk` structure, which only worked because the vulnerable code produced one literal SQL string. A parameterized query has no single string to inspect that way: the tests now build the real query via `PgDialect().sqlToQuery(result)` and assert on the compiled `sql` text plus the bound `params` array separately. This is the pattern to use for any future test asserting on drizzle-generated SQL in this codebase, not the old chunk-matching approach.
