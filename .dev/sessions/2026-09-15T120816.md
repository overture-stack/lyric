Added a per-file error summary endpoint and a CSV/TSV download for error details, addressing a large-submission scenario (thousands of invalid records, several errors each) where shipping the full raw per-record error list would mean a multi-MB payload just to render two dashboard numbers. The summary groups by fieldName, reason, and (for restriction violations) the specific restriction type, and lists the contributing record IDs per group.

- `packages/data-provider/src/utils/submissionTypes.ts`: `SubmissionRecordFieldError` carries `recordId` (required) and `restrictionType` (set only for `INVALID_BY_RESTRICTION`, naming which restriction failed, e.g. `required`/`range`/`regex`); `SubmissionErrorFieldReasonCount` carries `message`, `restrictionType`, and `recordIds` (deduped, ascending) alongside `count`
- `packages/data-provider/src/utils/submissionUtils.ts`: `mapSubmissionRecordErrorsToFieldErrors(errors, recordId)` stamps the originating record's id onto every flattened error; `groupFieldErrorsByFieldAndReason` groups by fieldName+reason+restrictionType (restriction violations on the same field no longer get lumped into one bucket) and carries one message per group, exact when the underlying library's message is already value-independent (`UNRECOGNIZED_FIELD`, restriction violations, confirmed via `lectern-validation`'s restriction test messages, which are fixed per rule type, not per invalid value) and a representative example otherwise; `formatFieldErrorsAsDelimitedText` unchanged, still used only by the download endpoint
- `packages/data-provider/src/repository/submissionRecordsRepository.ts`: `getErrorsByFileId` now selects `id` alongside `errors` (still skips `data` and the `submissionFiles` join)
- `packages/data-provider/src/services/submission/submissionService.ts`: `getSubmissionErrorsByFileId` (detail data feeding the CSV/TSV download) and `getSubmissionErrorsSummaryByFileId` both thread `record.id` through; `assertFileBelongsToSubmission` shared between them
- Removed the raw-JSON `GET /:submissionId/errors` endpoint (controller handler, route, and the now-orphaned `SubmissionErrorsResult` swagger schema) now that the summary and CSV/TSV download cover the two real frontend needs; the service method it used stays, since the download endpoint still calls it directly
- `apps/server/swagger/submission-api.yml`, `swagger/schemas.yml`: `SubmissionErrorsSummaryResult` documents `message`, `restrictionType`, and `recordIds`
- `.dev/tech-debt.md`: "download error report for a file" resolved; remaining open item narrowed to zipping per-file reports across a whole submission
- Tests: unit coverage for restriction-type splitting, message representativeness, and recordId dedup/sort ordering; integration coverage against a real Postgres container asserting `recordIds` against actual DB-generated ids for both a plain field error and a restriction-type split
